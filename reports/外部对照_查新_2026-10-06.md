## 一、已识别文献核实

### 1.1 MemMA（arXiv 2603.18718，EMNLP 2026 Main）—— M1 已核实

- 作者 Minhua Lin 等 8 人；v2 修订于 2026-09-03；官方代码 github.com/ventr1c/memma
- 前向路径：Meta-Thinker 产出结构化指导，同时调度 Memory Manager
  （原子操作 **ADD / UPDATE / DELETE / NONE**）与 Query Reasoner
  （Refine-and-Probe 迭代检索）。针对两种病症：**近视写入**（myopic construction，
  累积或覆盖冲突事实而不消解）与**无的放矢检索**（aimless retrieval）
- 后向路径：**在场自演化**——每个会话结束后三步：生成探针 QA（测事实回忆 /
  跨会话推理 / 时间推断）→ 对临时记忆做在场验证 → 失败触发修复动作
  （**SKIP / MERGE / INSERT**），在记忆定稿前修完
- 评测：LoCoMo，多骨干、即插即用改善三种存储后端；基线含 A-MEM / NaiveRAG /
  LangMem / LightMem

**与本项目对照**：他们协调"构造-检索-利用"的循环，把下游失败变成记忆库的修复信号；
解决的是"记错了**怎么修**"与"检索**怎么问**"。本项目解决的是**写入时**的决策
（该不该写、写哪条、以什么生命周期）与失效处置的**缓存代价**测量。两条正交，
但其探针 QA 思路对我们"判定缓存实测"（M3 未做部分）有直接参考价值。

### 1.2 Dependency-Guided Rollback Repair（arXiv 2608.10502）—— M2 已核实

- 作者 Caili Yu、Yiqi Wang、Jiaqi Zhang 等；2026-08-11 提交
- **任务形式化：故障后记忆恢复**（post-failure memory recovery）——给定失败执行与
  已诊断的错误记忆，恢复答案与持久状态，同时保留未受影响的工作
- 方法：从运行时溯源构建**类型化记忆-动作依赖图**；追踪显式下游依赖；
  保留有独立可信证据的候选；停用无支撑的记忆状态；只选择性重放与答案相关的计算
- 评测：150 例受控基准（3 个工具域 × 4 类记忆故障）+ 50 例 LongMemEval-V2 派生压力测试
- 数字：恢复率 **85.3%** 对次优 77.3%；**100% 保留良性记忆**；比反思类方法少 41.8%
  的模型调用；派生子集 68.0% 对 54.0%；claim invalidation F1 0.669 对 0.603
- 论文自述局限：不意味着 uniformly better 的轨迹重建；限于受控基准；
  **依赖上游诊断器**（自动诊断集成是 future work）

**与本项目对照**：他们的输入是"已诊断的错误记忆"，解决修复；本项目的折叠是**诊断之后
的处置方式**之一，且给出了处置策略的三维对照。另外两点直接影响我们：

1. **R5 有了具体外部基准**：他们用了 LongMemEval-V2 派生轨迹——待办清单 R5 计划引入的
   "外部可复现故障集"有了先例与可对齐口径。
2. 他们的四类记忆故障（poisoned / stale / misattributed / 语义漂移）可作为本项目
   staleness 实验故障类型扩展的参照。

## 二、查新发现：概念重叠必须承认的部分

### 2.1 商用产品已实现"哈希链审计 + 时间回滚"（M4 格式并非本仓库率先提出）

**Novyx Labs**（商用 agent 记忆产品）宣称的默认能力：每次记忆操作自动记入
**append-only 哈希链**审计（`audit_health()` 返回 `chain_valid`），提供
**time-travel rollback**（回滚到 poisoning 之前的状态点，预览要恢复/移除多少条）、
策略引擎在高危动作前拦截。

对照：这与本仓库 `memorycore/audit.py` 的哈希链、`rollback`、MCP 的 `memory_audit`
**同构**。因此 M4 的定位应是"**给出一个最小可验证格式并证明其可校验**"，
而不是"提出删除审计"。差异点仅在：我们的格式刻意**只记哈希不记内容**、
并在 MCP 用户可控层闭环（list / delete / audit）。

### 2.2 "冲突消解即防御"——折叠机制已被工程界当作安全层

**Ricord.ai 的六层防御模型（2026）**第 2 层："当新事实与既有事实矛盾时，不并存，
而是把旧事实标记为 superseded、新事实为 canonical，并保留审计轨迹"——并明确说这
**既是质量特性也是安全特性**（投毒必须"在正当性上赢过"取代规则，而不能靠并存
让模型随机挑错的那条）。其第 2 层还给出一条具体规则：**低可信来源的记忆不得取代
高可信来源的记忆**。

对照：这正是本仓库 staleness 折叠的语义（同键新条目取代旧条目、旧条目标记
`superseded_by`、留折叠记录）。结论：**"折叠即取代"的概念不能表述为由本仓库率先提出**；
本仓库的增量在三点——折叠策略的**三维对照实测**（回答质量 / 追问可答 / 缓存代价）、
折叠的**前缀稳定性处理**（原位占位），以及**LLM 语义判定驱动折叠**（字符判定零触发的
实证）。"低可信不得取代高可信"是一条可以直接吸收进 `MemoryEntry` 处置规则的建议，
尚未实现，如实记录。

### 2.3 对 M4 的尖锐外部批评：同一存储内的校验链不算完整性

**"A checksum inside the blast radius isn't integrity"（The Colony，2026 春季讨论）**
针对记忆投毒防御提出两个被普遍欠规范的问题：

1. **参考哈希放在哪**：如果攻击者能写记忆库，通常也能写完整性日志——
   "把哈希放在它所保护的东西旁边是表演"（theatre）。参考值必须位于记忆写入者
   **结构性够不到**的信任域。
2. **什么时候校验**：异常检测与周期审计都是"事后"——攻击的牙齿是 forever 这个词；
   有约束力的校验必须在**信任建立时刻**（boot 时、把记忆库当自己的过去之前）进行。

对照：本仓库 `audit.py` 的链**存在同一存储内**，因此它能证明的是
"记录未被**顺带/本地**改动、删除事件序列可复核"，**不能**对抗能重写整个存储的对手。
这条局限必须写进 M4 与 README 的边界声明。论文观察到的缓解方向（外生锚点、
boot 时校验）记录为 future work，不在本轮实现。

### 2.4 信任分防御的双向失败（写入时决策的外部证据）

**Sunil et al. 2026（arXiv 2601.05504 分析）**：MINJA 式查询投毒评测给出两个有用结论：

- **预存正确记忆大幅压低攻击成功率**（GPT-4o-mini：空记忆 ASR 62% → 有相关正确记忆
  6.67%）；**检索条数越多投毒越放大**（3 → 5 → 10 条：ASR 6% → 20% → 38%）
- **信任分防御双向失败**：要么保守到全拒（无用），要么给投毒条目打 1.0 信任
  （Gemini 实测 82 条全 1.0，事后 54 条是投毒）——**信任分退化成置信过滤器**

对照：这支持本仓库两个设计——(1) 写入时的结构化决策（ADD/UPDATE/FOLD/NOOP +
provenance + 来源白名单）比"给个分数"更可审计；(2) 我们不用连续信任分做门槛，
而用**离散的来源判定 + 明确拒绝路径**。同时 1.05504 的"预存正确记忆压制投毒"
为折叠（保持正确旧条目在场但被取代）提供了一个安全侧的旁证。

## 三、对定位与路线的影响（M5 的回答）

三者在"记忆出错"这件事上的分工：

| | 写入时决策 | 失效处置 | 事后修复 |
|---|---|---|---|
| **本仓库** | ADD/UPDATE/FOLD/NOOP 决策 + 审计（回答"**该不该写、该不该问**"） | 折叠（append-only 取代）+ **三维代价实测** | 仅限隔离/折叠/回滚（无依赖图） |
| MemMA | 构造与检索的协调（治近视写入、无的放矢检索） | — | 探针 QA → 在场验证 → 修复（定稿前） |
| Rollback Repair | — | 保留有独立支撑的候选、停用无支撑状态 | 依赖图追踪 + 选择性重放（故障后） |

M5 的结论（更新定位表述）：**我们解决"该问不该问、该写不该写"，MemMA 解决"构造与检索
怎么协调"，Rollback Repair 解决"记错之后怎么把状态修回来"**。三者不互斥；本仓库
独有的一根轴是**折叠/失效处置对前缀缓存的影响测量**——本轮检索未发现任何工作
把记忆操作当作缓存事件来测（这正是三定律与记忆的交点），如实标注为"未检索到"。

**吸收进路线的两条具体建议**（均未实现，先记录）：
1. 取代门控：低可信来源不得取代高可信来源（Ricord 第 2 层）。
2. M3 的"判定缓存实测"可借鉴 MemMA 的探针 QA 生成方式。
